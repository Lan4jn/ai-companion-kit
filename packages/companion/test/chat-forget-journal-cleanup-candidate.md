# 持久聊天遗忘与加密日志：隔离候选设计（未实现）

## 已证实的残留
生成读到的完整历史保存在批次 `history` 字段中，整个 journal 使用可复用的 AES-GCM 密钥加密。对 SQLite 的遗忘删除历史和写入墓碑后，阻塞的 ready/unknown 批次仍可用同一密钥解密出该历史。生成文本本身也可能包含历史信息，不能仅删 `history` 就认为完成遗忘。旧 journal 文件、临时文件、文件系统快照、备份和闪存磨损均可能保留旧密文；SQLite WAL 和其他副本也需独立评估。不能声称物理删除或合规已完成。

## 签名与不可重发约束
`outputTag` 对整份 history、inputs、segments 等做 HMAC 绑定，`positionTag` 和 `ackTag` 又绑定 outputTags。直接删除字段会破坏完整性，重签可能无意授权旧输出。unknown 不能由于清理而变成可重试；已发出的消息不能撤回。拒绝把含遗忘来源的任何受影响生成内容继续发出。保留最小化、不可逆的去重/状态墓碑时仍需评估其关联性，不能假定匿名。

## 安全候选（须另行实现并验证）
1. 将 provenance 改为不含正文的、与存储世代/撤销状态绑定的最小化校验凭据；校验仍须与发送共享跨进程锁并逐段进行，不能仅事前校验。旧格式保持失败关闭，不能把旧签名升级为自动发送授权。
2. 遗忘协调使用同一作用域锁，将 SQLite 撤销/墓碑作为持久权威，并在 journal 上记录可恢复的清理意图；任何崩溃重启都先检查墓碑/意图，缺证据一律阻塞发送，确保任何中间状态都不能复活被遗忘内容。对受影响批次做整批废弃，unknown 保留最小不可重发状态，不以重签修补现有输出。
3. 若需要密码学擦除，应设计受影响数据独立密钥和持久密钥撤销，覆盖历史快照、输入、输出及所有副本；不可直接丢弃共享 journal 主密钥，否则其他队列也不可用。密钥销毁、备份及崩溃恢复需要明确边界；仍不等于物理介质删除。
4. 先用真实 SQLite、journal fsync/rename、跨进程锁、SIGKILL 和受控存储故障逐个切断：墓碑前后、意图前后、日志替换前后、密钥销毁前后；检查重复输入、未知发送、已签收历史、部分多段、所有历史关联、备份与回滚，并独立审计后才考虑接入。跨 SQLite 与文件系统不具备天然原子提交；单靠标志文件或成功回调不能证明擦除。

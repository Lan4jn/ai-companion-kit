# Offline-only network namespace experiment

`DOUYIN_TEST_NETNS=1 node --test test/douyin-netns-host-proxy.test.js` requires network namespace privileges, `ip`, `socat`, OpenSSL, Playwright Core and the locally installed Chromium. No production service is changed or restarted. This fixture uses a generated certificate, a synthetic session and a fixed host-loopback TLS server; it must never be used with real credentials or connected to the real site.

Chromium runs in a new network namespace with only loopback. A local socat bridge to a host Unix socket reaches a narrowly scoped fixture-only CONNECT proxy. The host proxy checks the literal CONNECT authority and all synthetic DNS answers, and connects exclusively to the local mock TLS server. TLS remains end-to-end between Chromium and the mock; the browser pins the ephemeral mock certificate public key. The proxy is not a production proxy and intentionally cannot reach the Internet.

The test exercises a same-context challenge and synthetic POST login, cookie path isolation, separate-context isolation, direct IP and foreign-host rejection, redirected private address, mixed DNS rejection, WebSocket attempt, and direct kernel socket probes. It checks host private-server zero hits. WebSocket blocking here is browser routing, not a property of a CONNECT tunnel.

**Not production-ready:** CONNECT is opaque and cannot enforce method/path, reject same-origin WebSockets, inspect response redirects or prevent a permitted origin from receiving secrets. This experiment does not integrate the actual headed daemon, production authentication, network namespace lifecycle management, OS hardening against a compromised browser process, cross-domain cookie leakage instrumentation, or a real-site endpoint policy. Namespace privileges and filesystem/Unix-socket exposure also require a hardened launcher. Keep the existing default-deny production behavior; do not substitute this experiment for a security boundary or enable real-account login on its evidence.

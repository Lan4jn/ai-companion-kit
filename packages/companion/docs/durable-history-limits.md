# Durable chat history limits and safety

`Memory.logDurableTurn` keeps one immutable file per exact conversation and batch. The default limit is 5,000 directory entries (`maxDurableTurns` constructor option), with a 1 MiB maximum serialized new record. Unknown entries and crash leftovers consume capacity. At capacity, new commits fail rather than evicting any history or deduplication credential; an identical existing batch remains retryable. Already-existing data is not automatically truncated. Delivery can already have happened when history commit fails: preserve and recover the queue's `history-pending` acknowledgement, never resend on that basis.

Cooperating writers serialize via `durable-turns.lock`. A process crash can leave it behind; no automatic stale-lock removal is safe. An operator must stop all writers and inspect the journal and filesystem before recovery. This is not a lock protocol for older versions, arbitrary external writers, restored snapshots, or differing configured limits; do not run those concurrently.

The history record is currently also its replay credential. There is no independent proof that a credential is safe to delete, so there is **no automatic expiry, compaction, or forgetting of this store**. Memory-brain retention and forgetting do not automatically erase or suppress this separate store on every history read. Do not claim that a memory-brain forget removes durable chat history. Safe end-to-end forgetting requires a shared, crash-safe forget barrier applied to all readers and replay, independent long-lived replay credentials, and coordination with pending/unknown journal states and restore/rollback policy. Until that is implemented, administrative privacy requests must be treated as unresolved; never delete records or locks as a routine capacity remedy.

# Local OneBot trust: partial building block only

The durable queue remains disabled by default. Its live path still requires pinned WSS ingress and pinned HTTPS delivery; this change does not relax that requirement or affect ordinary OneBot chat. The existing OneBot connects as a WS client, while delivery uses a separate HTTP client. A successful loopback connection or a listening-port UID lookup alone cannot safely authenticate either peer: the listener can change between inspection and connect, proxies can forward remote events, and addresses are not process credentials.

`src/chat_unix_peer_gate.py` is an isolated Linux Unix-stream frame reader for a future broker. It obtains `SO_PEERCRED` from the connected socket before reading any payload, enforces an explicitly supplied UID (and optionally PID), limits frame size and applies a single read deadline. It is not wired into OneBot, the queue, or sender authorization. Same UID is the trust boundary, not a unique program identity; same-UID processes may impersonate one another. A PID must come from a separately supervised lifecycle, not request data, and PID reuse and descriptor passing need further controls. Do not use this gate by itself to authenticate HTTP/WS or upstream QQ identities.

To remove certificates safely, an actual trusted local supervisor/broker must establish both endpoints under its control, bind the authenticated connection itself to the OneBot stream and HTTP sending connection without check/connect races, reject proxy/redirect and non-loopback paths, and preserve owner-scoped provenance and unknown-outcome no-retry semantics. The present implementation does not establish these guarantees. A public or arbitrary LAN peer cannot be treated as local solely by configuration or by a claimed address. LAN HTTP/WS remains available to ordinary chat under the user's existing trust choice, but is not elevated to durable-queue authentication.

Synthetic checks: `python3 -m unittest test/chat_unix_peer_gate_test.py`; the OneBot pinned-auth and main durable tests remain separately runnable with Node's test runner.

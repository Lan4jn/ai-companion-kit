# Authenticated OneBot durable candidate

This is an opt-in composition API, not wired into the production chat loop. `createAuthenticatedOneBotQueueCandidate` defaults to disabled and starts no worker or listener. Supply a `DurableBatchCandidate` backed by an independently managed encrypted journal, a OneBot configured for pinned WSS ingress, a `createAuthenticatedOneBotSender` pinned HTTPS sender for the same owner, distinct 32-byte seal and selector keys, and a trusted local `generate` function. All key holders and code running as the same UID are trusted.

With `enabled: true`, pass the original authenticated OneBot callback object to `candidate.accept(msg)`. Call `candidate.form(session, count)` explicitly to generate and persist output from the authenticated, owner-bound input. Start the local Unix socket with `await candidate.startSender({socket})`; use the existing recovery inspection and selector signing client to explicitly authorize one segment. Close the returned service when finished. Do not expose the socket to untrusted local users. This API does not provision credentials, schedule generation, or automatically replay work.

The WSS connection verifies the OneBot **service**, not the identity of the upstream QQ user: sender IDs are assertions by that service, which must be trusted. HTTPS verifies the configured outbound service and restricts sends to the configured owner. Treat a claimed or ambiguous delivery as `unknown`; never automatically resend it. A complete rollback of the journal to an earlier valid snapshot is not detectable by its authentication alone; an independent monotonic authority and operational reconciliation would be needed before stronger replay guarantees can be claimed. The candidate is not production-ready without those operational controls and deployment-specific security review.

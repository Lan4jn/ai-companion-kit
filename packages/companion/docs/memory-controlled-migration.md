# Controlled offline legacy migration — disabled

**The migration API currently always rejects.** Do not follow the callback-based candidate instructions below as an operational procedure: caller-supplied callbacks cannot establish operator authorization or original-event provenance. A trusted offline authorization flow, durable selection-bound single-use audit, and an independently authenticated original-event verifier must be implemented and tested before enabling migration. No migration was performed.

## Historical candidate design (not operational)

This is not wired into startup, chat, a scheduler, or an operator UI. It migrates **one selected QQ private-message memory** from the legacy adapter ledger to the SQLite-FTS adapter; it does not migrate legacy chat turns, merged turns, autonomous sources, arbitrary JSON logs, AME, or records without adapter provenance. Do not enable it for production until a trusted independent original-message verifier and a trusted operator authorization path have been built and reviewed.

Construct `createMemoryBrain` with `enabled:true`, `backend:'sqlite-fts'`, the same private scoped directory, and trusted callbacks `authorize`, `recoveryAuthorization`, `migrationAuthorization(scope, source, evidence)`, and `verifyMigrationEvidence(record)`. The first three decisions must explicitly return `true` for the exact selection, before any source access. An absent callback disables the operation. The verifier must independently establish that the exact original event, text, scope, and evidence match; legacy metadata or LLM judgment is not independent proof. Call `migrateLegacyEvidence(scope, {source:'qq-private-message', evidence:'onebot-message:<canonical-id>'})` only while all non-cooperating writers and recovery processes are stopped. Existing participating forget writers are serialized by the shared source lock; do not call back into that lock from a verifier.

Returns only `{status:'inserted'|'duplicate'|'rejected'|'forgotten'}` and generic errors, without text or identifiers. The caller may count these outcomes as a privacy-preserving audit; no persistent audit sink is installed. Neither a result nor a callback is proof of owner consent: the trusted integration must obtain and record explicit owner consent separately, without logging content. Denials occur before source lookup. The selected ledger is read only; malformed data, conflicting identities, revocations, tombstones, missing original evidence, uncheckpointed WAL/journal files and unsupported scopes fail closed. No source is automatically scanned. Original timestamp is preserved and a stricter source retention is rejected rather than extended. Idempotency is by exact evidence and text/timestamp; conflicts fail closed.

The candidate management API now exposes `migrateLegacyEvidence(input)` only when a separate `authorizeManagement` callback and `migrationAudit` sink are provided. It writes content-free attempt and outcome events; if the attempt cannot be recorded it does not call the adapter, while an outcome audit failure reports an uncertain result because the write may already have happened. These events deliberately omit identifiers and cannot establish which selection was authorized or independently prove consent. The sink must itself provide durable, protected storage; this API does not install one. Management authorization denials are not audited by this sink. Existing direct adapter callers can bypass this management audit and must not be used as a production authorization path. The managed-store factory does not expose migration.

The underlying SQLite destination is created only after authorization and verification. As with the existing adapter, rollback protection depends on a fresh trusted recovery authorization and complete coordinated backup/restore; there is no independent anti-rollback authority. This API does not itself authenticate the owner or implement the verifier. No real-data migration was performed.

# OneBot queue bridge candidate (not enabled)

This is an opt-in in-process composition, not a general OneBot HTTP proxy. The process already holding the encrypted journal lock and the existing OneBot object can call `startOneBotQueueBridge` with `enabled: true`, the queue, the bot, `ownerId`, separate 32-byte `sealKey` and `selectorKey`, a private absolute socket path, and `connectionIsAuthenticated: true`. The final flag is an explicit assertion by trusted composition code, **not evidence or verification of endpoint authentication**. Do not start this candidate unless the actual connection's authentication and identity have been independently established; existing plain TCP/WS is not sufficient. It is not wired into production startup.

The bridge only accepts newline-delimited, signed `{id,snapshot,confirm,signature}` selectors. It resolves the current row internally, validates the existing cryptographic output, position and owner/private-destination bindings, commits unknown before sending, and never automatically retries unknown. The existing client supports `--selector-key /private/path` (32 raw bytes, owned by the process UID, mode 0600, no hard links); use the existing explicit one-segment confirmation and selector. A missing signature is blocked when connected to this bridge. Existing legacy unsigned sender candidate remains separate and must not be substituted for this bridge.

Trust boundaries: the selector-key holder may select any eligible already-authorized batch; no arbitrary message or destination is accepted. The seal-key holder and trusted generation/transport code can authorize outputs and are fully trusted. The socket directory and socket are restricted to the owner UID, but Node does not verify peer credentials here: processes sharing that UID, root, the host administrator, and code able to inspect or modify the process/files are in the trust domain. This is not isolation from a malicious same-UID process. Protect the key and directory accordingly, isolate untrusted code under another UID, and do not treat path ownership as remote endpoint authentication. The existing socket client checks ownership before connect; this is not a defense against a malicious same-UID path replacement.

Treat any timeout or unavailable result as unknown and inspect the journal offline before action; never blindly resend. This candidate does not solve production rollout, startup recovery, operator key provisioning, or independent OneBot authentication. No production configuration was changed.

# Durable chat queue integration: blocked (candidate only)

`ChatBatchQueue` remains in-memory by default. Passing any `durable` value other than `false` to its constructor fails closed; it does **not** activate persistence. No production configuration switch is installed. `chat-durable-runtime-candidate.js` remains an isolated candidate, not a production queue. Do not rely on restart for recovery of the current in-memory queue.

## Blocking defects

- `add()` synchronously hands individual messages to the in-memory `Waker`; batching and timeout-driven flush mutate volatile state. The candidate stores one JSON payload per independent `append` and cannot atomically persist the input, batching boundary and acceptance as one queue operation. Persisting only at `enqueue` loses accepted, unflushed messages. Persisting each input without a durable batch transition cannot reproduce the exact turn after a crash.
- OneBot message trust is an object capability in a `WeakMap`; JSON serialization loses it. Restoring the capability from disk without a new authenticated provenance design could improperly grant owner privileges or change behavior.
- `handleTurn` has bare returns, including paths with `bot.send` and other side effects; these do not distinguish delivered, confirmed-unsent, skipped, partial or unknown. The candidate retires only explicit `{ok:true}`; the existing queue treats non-false/undefined as successful. Neither provides a reliable complete turn outcome for all paths, and a missing response is not proof of no delivery.
- Candidate claims persist `unknown` before running, and the first unknown blocks its session; it cannot safely auto-retry. Its separate local recovery mechanism is not authenticated human verification; enabling it is outside this integration. A crash after delivery and before retirement necessarily requires manual reconciliation. Existing in-memory recovery cannot safely stand in for journal reconciliation.
- Candidate's cooperative lock and local fsync/rename assumptions do not provide rollback protection or distributed-writer fencing. Startup replay, stale lock clearance, key lifecycle and production deployment need independent review.

## Candidate private-delivery binding

`createBoundOneBotDeliveryCandidate` is an isolated, default-disabled adapter. It authenticates every sealed input against the claimed session and derives the private destination from those inputs rather than trusting a caller-supplied recipient; it does not recreate a trusted event. A mismatch, exception, or uncertain send leaves the precommitted claim unknown and blocks automatic resend. OneBot acknowledgement proves only transport acceptance. This closes a candidate-level destination binding gap, **not** the production integration blockers below: the endpoint, key management, journal integrity/rollback model, turn outcomes and reconciliation still require independent review. Do not wire this adapter to production yet.

## Current production-loop boundary (reviewed against the newer candidate)

The later authenticated ingress and signed-segment candidates improve the isolated design, but do not implement this production path. `src/index.js` still constructs `ChatBatchQueue` and passes its batches to `handleTurn`; it does not create `createAuthenticatedOneBotQueueCandidate`. The latter only accepts and forms data and offers an explicitly invoked sender: it does not schedule a production turn or preserve its existing semantics. Do not interpret the candidate tests as production integration.

`handleTurn` is not a pure generator: it can invoke game control, send images or voice, execute model tools, update state and send multiple text segments. Its ordinary generation call permits tools. The candidate calls `generate` before it durably forms a batch, so passing `handleTurn` or a generator with these effects would allow them to run before a durable effect claim, and re-forming after a crash could repeat effects. Conversely, disabling tools and replacing the turn with a text-only generator would silently change normal owner chat. The candidate's whole-turn marker avoids automatic retry but does not provide an accurate recovery record for individual sends and tool effects; it must not be promoted as segment-safe wiring.

A safe production slice requires, at minimum: (1) an explicitly configured, genuinely authenticated WSS ingress and HTTPS sender bound to the same trusted service and owner, with no fallback to the current plaintext endpoint; (2) a durable, serialized transition before every effectful turn or tool, with unknown outcomes blocking replay and reconciliation handling partial delivery; (3) a generation/delivery split preserving current chat, tool, media, memory and trust behavior without reissuing serialized object capabilities; and (4) a rollback/fencing and operational reconciliation policy. The TLS peer asserts the upstream QQ identity; TLS alone does not independently authenticate that identity. The current plaintext OneBot connection cannot satisfy (1). No production switch should be added until these boundaries have been implemented and independently tested.

## Required before optional wiring

Define a versioned atomic journal state machine covering accepted inputs, durable batch formation, claim and explicit delivery/side-effect outcomes; bind replay provenance without forging OneBot capabilities; require precise outcomes for every `handleTurn` exit; preserve per-session ordering and stop at unknown; design authenticated reconciliation, shutdown, capacity and crash tests. Only then expose a deliberately enabled deployment path with no volatile fallback. Test using isolated synthetic data and crash injection; never use production records or keys for those tests.

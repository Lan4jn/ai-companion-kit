# AME experimental application selection

`memoryBrain.enabled` remains off unless explicitly enabled. A trusted operator can explicitly select `memoryBrain.backend: "ame"`; omission selects legacy and unknown enabled backends are rejected. The configured `python` must be an absolute interpreter with the compatible `agent_memory` package installed; the ordinary system Python may not contain it. AME uses a separate `ame-v1-*.sqlite3` ledger; existing legacy records are neither migrated nor automatically imported. Existing managed-store initialization, trusted scope/source authorization and restore review requirements still apply. Backend selection is propagated to chat recall, native-source filtering, and the optional durable-chat store. Unavailable or unauthorized memory filtering fails closed rather than falling back to another backend.

An additional explicit `memoryBrain.backend: "sqlite-fts"` selects the local Python standard-library sqlite3/FTS5 worker, not AME. It requires Python's SQLite to support FTS5; unavailable FTS5 fails closed. It uses a separate `sqlite-fts-v1-*.sqlite3` ledger, with no migration or import. Its bounded lexical FTS and literal Han-span/question-fragment matching are not embeddings, semantic search, or an exact ranking equivalence to AME. Production remains disabled by default; omission still selects legacy.

Cooperative forget filtering consults all three backends for the exact scope/source; only the exact canonical `https://tieba.baidu.com/p/<id>` identity is linked between `tieba` and `web-source-page`. Noncanonical thread candidates are excluded; arbitrary historical aliases and other cross-source relationships are not proven. Review and reconcile legacy data manually before relying on cross-source erasure. Filesystem access by the same UID, the process, configuration and trusted operator remain trusted; no independent rollback authority exists. This experimental integration is not a blanket privacy, source-coverage, licensing or production readiness audit.

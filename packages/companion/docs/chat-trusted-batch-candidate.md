# Trusted durable batch candidate

This is an isolated, explicitly enabled candidate, not production wiring or an automatic startup replay. The production durable queue remains disabled. The caller must authenticate and isolate the OneBot endpoint and provide an owner ID and a 32-byte external seal key. The caller must retain exclusive control over the key, generator function and in-process composition; never expose those capabilities to message content or untrusted plugins. A parser snapshot alone does not authenticate upstream identity.

`createTrustedBatchGenerationCandidate` accepts authenticated owner-private input snapshots and calls its locally injected trusted generator once. A private, one-use, process-local capability authorizes forming only the exact selected input records and exact returned segments. Each output MAC binds the complete ordered input records and IDs, batch ID, session, owner-private destination, entire ordered output, and segment index/content. A separate progress MAC authenticates state, attempt and position. `createBoundOneBotDeliveryCandidate` verifies all segments and input seals before claim, persists an authenticated unknown attempt before sending, and advances only on explicit OneBot acknowledgement. Acknowledgement means transport acceptance, not proof of display. Reopening never reruns generation or tools. Unknown attempts and old unbound batches are blocked; any reconciliation needs an independently authorized mechanism, which this candidate does not provide.

The generator must return the final literal text segments; tool markup, CQ syntax, altered outputs and invalid responses are refused. The capability does not make an untrusted injected generator trustworthy. Protect the external key and filesystem; hostile same-UID processes or code able to access the key or modify the process are outside this boundary. Full authenticated journal rollback (including an old ready state) cannot be detected without an independent monotonic external anchor. Do not use this candidate if these assumptions cannot be met. The generic, separately enabled delivery candidate does not provide these provenance guarantees and must not be used for this owner-bound workflow.


## Manual ready-segment recovery candidate

No production connection is supplied. A separate journal-owning restricted sender candidate with its own selector protocol is described in [chat-trusted-sender-candidate.md](chat-trusted-sender-candidate.md); it is not compatible with the raw socket protocol below and is not production wiring. Stop all journal writers first, use a trusted private local filesystem, and run only as the key/socket owner. Never remove a live or unexplained stale lock. Inspect discloses the current segment and session to stdout; use a private terminal and protect output:

```
node scripts/chat-trusted-recovery.mjs inspect --directory /absolute/private/journal --key /absolute/private/journal-key
node scripts/chat-trusted-recovery.mjs send --directory /absolute/private/journal --key /absolute/private/journal-key --seal-key /absolute/private/seal-key --owner OWNER_ID --socket /absolute/private/sender.sock --id BATCH_ID --snapshot INSPECT_SNAPSHOT --confirm-one-segment
```

The socket is an independently supplied, trusted, same-owner private Unix socket service. It must authenticate/isolate its own OneBot endpoint and use the existing OneBot outcome semantics. It receives one newline-delimited JSON object `{ "destination": "private:...", "segment": "..." }` and returns one newline-delimited JSON OneBot adapter response, e.g. `{ "ok": true, "data": { "status": "ok", "retcode": 0 } }`. No such service or production adapter is installed by this candidate. Never point it at an untrusted service. Each invocation selects exactly one current ready segment and requires a fresh matching snapshot and explicit confirmation; snapshots are change detectors, not signatures. The actual send verifies input, output, destination and progress MACs under the separate seal key and durably marks the attempt unknown before socket connection. Inspection alone does not authenticate a row. A blocked/stale selection sends nothing; timeout, disconnect, negative/ambiguous response or crash after claim leaves unknown and cannot be retried automatically or by this CLI. It cannot reconcile unknown, prove display, undo a send, or rerun generation/tools. Even transport acknowledgement only establishes transport acceptance. This socket service is a privileged capability: it must not duplicate requests or report acceptance speculatively.

Neither MACs, snapshots, nor encrypted journal detect restoration of a complete older authentic ready journal: replay prevention across full rollback requires an independent durable monotonic anchor, which is not implemented. Never restore an older journal and use this command without independently resolving all potential sends; do not use at all when rollback cannot be excluded. OS permissions and cooperative locking do not defend against hostile same-UID processes, local administrators, malicious sender service, or code with key access. Partial journal writes and stale locks require offline investigation; do not bypass them.
